# QuickBite — Notification Rules Specification

**File:** `docs/notifications/NOTIFICATION_RULES.md`
**Version:** 1.0
**Status:** Specification
**Phase:** 7 — Notifications & Realtime

---

## 1. Purpose

This document defines the complete notification architecture and business rules for QuickBite.

Notifications communicate important events to:

* Customers
* Restaurant Owners
* Restaurant Operators
* Riders
* Admins
* Super Admins

Notifications may be delivered through:

* In-app notifications
* Push notifications
* SMS
* Email

The notification system must be reliable, idempotent, secure, auditable, configurable, and integrated with the backend event system.

The backend is authoritative for notification triggering.

Clients must never decide independently that a notification should be sent.

---

# 2. Core Principles

## 2.1 Backend Authority

Notification triggers are generated by backend business events.

Examples:

```text
Order accepted
Order preparing
Order ready
Rider assigned
Payment succeeded
Payment failed
Order cancelled
Restaurant application approved
Password changed
```

The frontend must not directly trigger transactional notifications.

---

## 2.2 Event-Driven Notifications

Business modules generate internal events.

Example:

```text
Order status changes:
PREPARING
        ↓
OrderStatusChanged event
        ↓
Notification worker
        ↓
Customer notification
        ↓
Push + In-App
```

The notification system consumes events rather than embedding notification logic throughout unrelated modules.

---

## 2.3 Outbox Integration

Critical notification-triggering events must use the existing `outbox_events` architecture.

Transaction:

```text
Business Transaction
        ↓
Database State Change
        ↓
Outbox Event
        ↓
Background Worker
        ↓
Notification Processing
        ↓
Provider
```

The system must avoid situations where an order changes successfully but its notification event is silently lost.

---

# 3. Notification Channels

QuickBite V1 supports four channels.

## 3.1 In-App

Stored in:

```text
notifications
```

Used for:

* Order updates
* Payment updates
* Promotions
* Support
* Account notifications
* Administrative messages

In-app notifications remain available even when push delivery fails.

---

## 3.2 Push

Push notifications are used for time-sensitive events.

Examples:

* New restaurant order
* New rider delivery offer
* Rider assigned
* Order ready
* Order delivered
* Payment failure
* Security events

Push delivery depends on the device/provider infrastructure.

Provider-specific logic must be isolated behind a notification provider abstraction.

---

## 3.3 SMS

SMS is reserved for important transactional or security events.

Examples:

* OTP
* Critical account verification
* Selected order updates
* Important delivery communication where configured

SMS must not be used for every application event.

SMS provider failures must not corrupt the underlying business transaction.

---

## 3.4 Email

Email is used for:

* Account verification
* Password reset
* Important account/security events
* Restaurant application updates
* Financial documents
* Settlement information
* Support communications
* Selected order confirmations

Email is generally not the primary channel for highly time-sensitive dispatch events.

# 5. Notification Priority

Notifications have a priority.

```text
LOW
NORMAL
HIGH
CRITICAL
```

## LOW

Examples:

* Promotional information
* Non-urgent informational messages

## NORMAL

Examples:

* Order confirmation
* Order accepted
* Order delivered
* Settlement generated

## HIGH

Examples:

* New restaurant order
* Rider delivery offer
* Payment failure
* Order cancellation
* Restaurant application decision

## CRITICAL

Examples:

* Security-related account events
* Account compromise warnings
* Critical operational alerts

Priority affects:

* Processing order
* Retry strategy
* Provider selection
* Push behavior
* Worker handling

Priority must not bypass authorization.

# 7. Notification Template Architecture

Notification content must not be scattered throughout controllers.

Templates should define:

```text
notification_type
channel
title_template
body_template
locale
variables
enabled
version
```

Example:

```text
Type:
ORDER_ACCEPTED

Channel:
PUSH

Title:
Order accepted

Body:
{restaurant_name} has accepted your order #{order_number}.
```

Templates should support localization.

# 10. Restaurant Notifications

Restaurant Owners and Operators may receive:

* New order
* Order cancellation
* Customer order changes where supported
* Payment/order issues
* Restaurant application status
* Restaurant status changes
* Important platform announcements
* New review
* Support updates
* Settlement created
* Payout completed/failed
* Menu or account administrative events

New order notifications are high priority.

Restaurant notification authorization must respect restaurant tenant isolation.

An Operator must only receive notifications for restaurants they are authorized to operate.

---

# 11. Rider Notifications

Riders may receive:

* Account verification result
* Account approval/rejection
* New delivery offer
* Delivery offer expiration
* Delivery assignment
* Pickup reminders
* Customer delivery information required for active delivery
* Delivery completion
* Earnings generated
* Settlement/payout updates
* Support messages
* Security events

Delivery offers are time-sensitive and should use realtime + push where supported.

---

# 12. Admin Notifications

Admins may receive:

* Restaurant application submitted
* Rider application submitted
* High-risk activity
* Payment failures
* Refund issues
* Settlement failures
* Support escalation
* Operational alerts
* System alerts

Admin notifications must respect admin permissions.

Sensitive information must not be included unnecessarily in push notifications.

---

# 13. Super Admin Notifications

Super Admins may receive additional system-level notifications.

Examples:

* Security incidents
* Critical infrastructure alerts
* Financial processing failures
* Configuration changes
* Administrative permission changes
* High-severity risk events

Super Admin notifications must be protected with stronger authorization.

---

# 14. Notification Preferences

Users may configure allowed notification categories where appropriate.

Example:

```text
Order updates        ON
Promotions           OFF
Reviews              ON
Support              ON
Security             ALWAYS ON
```

Security and certain transactional notifications cannot be disabled where required for account safety or service operation.

Users must not be allowed to disable mandatory authentication/security messages.

---

# 15. Transactional vs Promotional Notifications

Notifications must be classified as:

```text
TRANSACTIONAL
PROMOTIONAL
SECURITY
```

## Transactional

Required to operate the service.

Examples:

* Order accepted
* Payment result
* Delivery status

## Promotional

Marketing-related.

Examples:

* Discount campaign
* Promotional offer
* Restaurant promotion

Promotional notifications must respect user preferences and applicable communication requirements.

## Security

Account protection.

Examples:

* Password changed
* New login
* MFA changed

Security notifications are not treated as promotional messages.

---

# 16. Notification Deduplication

The same event must not generate duplicate notifications unintentionally.

Each notification event should have a deterministic idempotency key.

Example:

```text
order:{order_id}:status:{status}:user:{user_id}
```

For provider delivery:

```text
notification_id + channel
```

must uniquely identify a delivery attempt series.

Duplicate workers must not create duplicate logical notifications.

---

# 17. Retry Policy

Transient provider failures should be retried.

Recommended strategy:

```text
Attempt 1
    ↓
short delay
    ↓
Attempt 2
    ↓
longer delay
    ↓
Attempt 3
    ↓
backoff
    ↓
final attempt
```

The exact retry configuration must be environment/config driven.

Permanent failures should not be retried indefinitely.

Examples of permanent failure:

```text
invalid destination
invalid device token
invalid email address
provider rejection
```

---

# 18. Failed Notification Handling

A failed notification must not normally fail the business transaction.

Example:

```text
Order accepted
    ↓
Database commit succeeds
    ↓
Notification queued
    ↓
Push provider fails
```

The order remains accepted.

The notification system records the failure and applies its retry policy.

---

# 19. Notification Delivery Records

The existing:

```text
notification_deliveries
```

table records channel-level delivery state.

Recommended statuses:

```text
PENDING
PROCESSING
SENT
DELIVERED
FAILED
EXPIRED
```

Provider message IDs should be stored when available.

---

# 20. Push Token Management

The backend must maintain registered device tokens.

Tokens should be associated with:

```text
user_id
device_id
platform
push_token
last_seen_at
active
```

Invalid tokens must eventually be disabled.

Users may have multiple devices.

Logging in on a new device must not automatically invalidate all existing devices unless security policy requires it.

---

# 21. Notification Security

Notifications must never expose unnecessary sensitive information.

Avoid including:

* Passwords
* OTP values except through approved secure OTP flows
* Payment credentials
* Full sensitive documents
* Internal risk scores
* Internal fraud signals
* Private administrative information

Push notifications may be visible on a locked device.

Sensitive notification bodies should therefore be minimized.

Example:

Instead of:

```text
Your account password was changed from IP 192.168.x.x using device...
```

Prefer:

```text
Your QuickBite password was changed. Open the app if this wasn't you.
```

---

# 22. Notification Authorization

Before generating a notification:

```text
Event
 ↓
Determine recipient
 ↓
Verify recipient relationship
 ↓
Verify tenant/resource access
 ↓
Generate notification
```

Examples:

A restaurant operator must not receive another restaurant's order notification.

A rider must not receive another rider's customer information.

A customer must not receive another customer's order updates.

---

# 23. Order Notification Rules

Order notifications should correspond to actual backend state transitions.

Example:

```text
PENDING
    ↓
RESTAURANT_ACCEPTED
```

Generate:

```text
ORDER_ACCEPTED
```

Then:

```text
RESTAURANT_ACCEPTED
    ↓
PREPARING
```

Generate:

```text
ORDER_PREPARING
```

The system must not send an `ORDER_DELIVERED` notification unless the backend order state actually reaches:

```text
DELIVERED
```

---

# 24. Cancellation Notifications

When an order is cancelled:

```text
Order cancellation transaction
        ↓
Order status history
        ↓
Cancellation record
        ↓
Outbox event
        ↓
Notification worker
```

Recipients depend on cancellation actor and business context.

Examples:

Customer cancellation:

```text
Restaurant may receive cancellation notification.
```

Restaurant cancellation:

```text
Customer must receive cancellation notification.
```

Admin cancellation:

```text
Relevant parties receive notification.
```

Refund information should be included when appropriate.

---

# 25. Dispatch Notifications

Dispatch events are time-sensitive.

### Rider

When an eligible rider receives an offer:

```text
Realtime event
+
Push notification
```

When offer expires:

```text
Realtime state update
```

### Customer

When rider assignment occurs:

```text
Rider assigned notification
```

The notification must not reveal unnecessary rider personal information.

---

# 26. Restaurant New Order Notifications

When an order is created successfully and restaurant is the intended recipient:

```text
Order Created
    ↓
Restaurant New Order event
    ↓
In-App
+
Push
+
Realtime
```

The restaurant UI must still retrieve authoritative order data from the backend.

A notification payload must not be treated as the authoritative order record.

---

# 27. Payment Notifications

Payment notifications are generated from backend payment state.

Examples:

```text
PAYMENT_SUCCEEDED
PAYMENT_FAILED
PAYMENT_REFUNDED
```

The client must not determine payment success based only on a provider redirect or frontend callback.

---

# 28. Settlement and Payout Notifications

Restaurant and rider financial notifications may include:

* Settlement generated
* Settlement finalized
* Payout initiated
* Payout completed
* Payout failed

Amounts must come from authoritative financial records.

---

# 29. Support Notifications

Support events may generate:

```text
SUPPORT_TICKET_CREATED
SUPPORT_TICKET_UPDATED
SUPPORT_TICKET_MESSAGE
SUPPORT_TICKET_RESOLVED
```

Only authorized ticket participants receive notifications.

---

# 30. Security Notifications

Security events may include:

```text
SECURITY_NEW_LOGIN
SECURITY_PASSWORD_CHANGED
SECURITY_MFA_CHANGED
SECURITY_SESSION_REVOKED
```

Security notifications should be prioritized above promotional notifications.

# 31. Background Worker Architecture

Notification processing should occur asynchronously.

Example:

```text
Application
    ↓
Database Transaction
    ↓
Outbox Event
    ↓
Outbox Worker
    ↓
Notification Job
    ↓
Notification Worker
    ↓
Provider Adapter
    ↓
Delivery Record
```

This prevents slow third-party providers from blocking API requests.

---

# 32. Provider Abstraction

The application must not tightly couple business logic to a specific provider.

Use interfaces such as:

```text
PushNotificationProvider
SmsProvider
EmailProvider
```

Example:

```text
NotificationService
        ↓
PushProvider
        ↓
Provider implementation
```

Provider credentials must be stored securely.

---

# 33. Notification Queue

Notification jobs should include:

```text
notification_id
user_id
channel
priority
attempt_count
available_at
expires_at
created_at
```

High-priority notifications may be processed ahead of low-priority notifications.

---

# 34. Expiration

Time-sensitive notifications may expire.

Example:

```text
Rider delivery offer
```

If the offer is already expired, the notification should not be delivered as an actionable offer.

The backend offer state remains authoritative.

---

# 35. Offline Users

If a user is offline:

* In-app notification is stored.
* Push may be attempted.
* Realtime event is not expected to be received.
* On reconnect, client fetches authoritative state.

Realtime delivery is therefore supplementary rather than the only source of truth.

---

# 36. Localization

Notification templates should support localization.

Minimum architecture:

```text

channel
template_version
```

The user's configured language should determine the template where available.

If a translation is unavailable, use the configured fallback locale.

# 39. Read State

A notification may transition:

```text
UNREAD
    ↓
READ
```

Read state is user-specific.

Reading a notification must not delete the notification.

# 42. Rate Limiting

Notification generation must be protected from abuse and accidental loops.

Examples:

```text
Password reset request
OTP request
Promotional campaign
Support notification
```

Rate limits must be configurable.

---

# 43. Notification Loop Prevention

A notification must never recursively generate another notification unless explicitly designed.

Example:

```text
Notification failed
    ↓
Do not generate another user notification
```

Provider failure should update delivery state rather than trigger an infinite event loop.

---

# 44. Failure Isolation

Failure of:

```text
Push provider
SMS provider
Email provider
```

must not bring down:

```text
Order service
Payment service
Dispatch service
```

Provider failures must be isolated.

# 46. Definition of Done

Notification functionality is complete only when:

* Trigger is documented.
* Recipient is defined.
* Authorization is implemented.
* Template exists.
* Channel behavior is defined.
* Preference behavior is defined.
* Idempotency is implemented.
* Retry behavior is implemented.
* Failure handling exists.
* Outbox integration exists where required.
* Delivery records are stored.
* Security controls exist.
* Logging/metrics exist.
* Unit tests exist.
* Integration tests exist.
* E2E tests exist where applicable.
* API documentation is updated.
* No business logic depends on frontend notification behavior.
